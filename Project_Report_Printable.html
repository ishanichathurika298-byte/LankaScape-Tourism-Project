1. Executive Summary & Problem Domain

LankaScape is a modern, enterprise-grade inbound tour operating web application engineered specifically for Sri Lanka's inbound tourism sector. Representing an SLTDA-certified inbound travel agency headquartered at the World Trade Center (WTC), Colombo 01, the system bridges the gap between international tourists and authentic Sri Lankan travel logistics.

Prior to this application, travelers encountered fragmented planning: destination sanctuary entry tickets, highway transport from Colombo, registered tourist guides, dining plans, and accommodation were dispersed across unrelated vendors. LankaScape unifies these logistics into an integrated, transparent, and responsive platform.

Key Achievement: Strict compliance with the EE4207 Web Application Development Mini Project Rubric, achieving full CRUD functionality on persistent MySQL entities, robust client and server validation, multi-criteria filtering, relational database integrity, and modern responsive UI design.

3. Database Design & Relational Schema (4 Marks)

The database schema is designed in Third Normal Form (3NF) to eliminate redundancy and maintain referential integrity across all travel entities.

3.1 Entity Relationship Diagram (ERD)

Table Name Primary Key Foreign Keys Description & Constraints
`users` `id` (BIGINT) None Registered travelers. Enforces `UNIQUE` constraint on `email`.
`destinations` `id` (BIGINT) None Pre-seeded with 60 authentic attractions across 5 travel categories with Colombo distance and travel times.
`bookings` `id` (BIGINT) `user_id` → `users(id)`
`destination_id` → `destinations(id)`		 Transactional core record. Holds itemized costs, travel date, fleet, guide, meals, accommodation, payment status, and transaction ID.

3.2 Table Schema: `bookings` (Main Transaction Entity)

CREATE TABLE `bookings` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT NOT NULL,
  `destination_id` BIGINT NOT NULL,
  `booking_date` DATE NOT NULL,
  `travel_date` VARCHAR(50) NOT NULL,
  `quantity` INT NOT NULL,
  `pickup_location` VARCHAR(255) DEFAULT 'Colombo City Hotel',
  `vehicle_type` VARCHAR(100) DEFAULT 'Private AC Sedan',
  `guide_type` VARCHAR(100) DEFAULT 'Chauffeur Guide',
  `meal_plan` VARCHAR(100) DEFAULT 'No Meal Plan',
  `hotel_name` VARCHAR(100) DEFAULT 'Day Tour',
  `payment_method` VARCHAR(50) DEFAULT 'Visa',
  `payment_status` VARCHAR(50) DEFAULT 'PAID',
  `transaction_id` VARCHAR(100),
  `ticket_cost` DOUBLE, `transport_cost` DOUBLE, `guide_cost` DOUBLE,
  `meal_cost` DOUBLE, `hotel_cost` DOUBLE, `total_price` DOUBLE NOT NULL,
  PRIMARY KEY (`id`),
  CONSTRAINT `fk_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_dest` FOREIGN KEY (`destination_id`) REFERENCES `destinations` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

5. Validation & Robust Error Handling (2 Marks)

To ensure security and data consistency, validation is enforced at both client and server layers:

  • Client-Side Validation: Past dates are disabled (`min="today"`). Passenger quantity is bounded ($\ge 1$). Credit card format requires 16 digits, valid MM/YY expiration regex, and a 3-digit CVV. Password confirmation matching is enforced on registration.
  • Server-Side Validation: Spring Boot checks non-empty travel dates, rejects quantities $\le 0$ with `400 Bad Request`, verifies user and destination existence (`404 Not Found`), and independently calculates pricing server-side to prevent tampering.
